# m25 — iOS 27 motion: real curves, real springs, Material gone, 2026-10-17

## First, the finding that forced a rewrite

The request was to extract iOS 27 animation and motion from the IPSW. **It
cannot be extracted, and that is a measured result, not a guess.**

| Source searched | Result |
|---|---|
| `iPhone12,1_27.2_24B5099f_Restore.ipsw` | **122 entries, no `Payload/`.** It is a firmware-only IPSW — dyld caches, `.dylib`s and framework binaries are all absent. There is no UIKitCore anywhere. |
| `ios-ui-analysis/all-plists/` | 30,637 files, all `Info.plist`. Grepping for spring/curve/duration keys gives 420 hits, **all `springboard` path fragments**, not animation keys. |
| `ios-ui-analysis/all-metal-shaders/` | 300 entries, all compiled `.metallib`, **no `.metal` source**, and they are PBR/raytracing rather than UI motion. |
| `control-center/*_ios27_Info.plist` | These DID yield real layout data. They carry **no motion keys**. |
| `all-dylibs/` | 44 files, all DriverKit `libsystem_*.dylib`. |
| `extracted_ipsw/` | Firmware images only. |

So there is no compiled iOS animation constant on this machine to read. iOS does
not ship its motion in plists; it is compiled into UIKit/CoreAnimation as
immediates.

## What was there, and what it cost

`MotionTokens.kt` said "Apple publishes no numeric spring, duration or curve
table" and carried the **Material Design 3 duration ramp** (83/120/167/220/333/
400/500 ms) labelled as NOT-iOS, plus four curves of which exactly **one** was a
genuine Apple curve:

| Token | Was | Is it Apple? |
|---|---|---|
| `easingIOSDefault` | `(0.42, 0, 0.58, 1)` | **yes** — UIKit easeInOut |
| `easingStandard` | `(0.42, 0, 0.2, 1)` | **no** — Material fast-out-slow-in |
| `easingEmphasis` | `(0.2, 0, 0, 1)` | **no** — Material |
| `easingStandardAccelerate` | `(0.4, 0, 1, 1)` | **no** — Material |
| `easingStandardDecelerate` | `(0, 0, 0.2, 1)` | **no** — Material |
| all 8 durations | Material ramp | **no** |

Every call site that asked for "the iOS curve" got Material.

## What replaces it

### 1. The four UIKit easing curves, control points transcribed

```
linear     (0.00, 0.00) -> (1.00, 1.00)
easeIn     (0.42, 0.00) -> (1.00, 1.00)
easeOut    (0.00, 0.00) -> (0.58, 1.00)
easeInOut  (0.42, 0.00) -> (0.58, 1.00)
```

Source: nilcoalescing.com/blog/AnimationTimingInSwiftUI, which enumerates each
preset's control points explicitly and links each to its Apple documentation
page. Plus `circularEaseInOut`, which Apple also ships (a quarter-circle arc,
flatter at the ends and steeper through the middle than the bezier form).

`easingStandard` is now an **alias of `easingIOSDefault`** rather than a
separate Android curve, so the five existing call sites asking for it get the
real thing.

### 2. The fact that actually explains iOS feel

> "Since iOS 17, the `.default` option is a spring animation with a
> configuration chosen by Apple."

This is why no duration ramp can substitute. A spring carries **velocity
continuity**: it picks up the velocity it already had and decelerates into the
target, so an interrupted animation continues instead of restarting from zero.
A fixed-duration ease has no such property at any duration you tune it to. That
is why iOS gestures feel attached to the finger and Material's 200 ms eases do
not.

AppleUX now expresses user-caused motion as springs. Durations survive only
where a spring is genuinely wrong: continuous loops, and reveals the user did
not cause.

### 3. Springs — solved, not eyeballed

Apple describes `.smooth`, `.snappy` and `.bouncy` **qualitatively**
(critically damped / slightly underdamped / clearly underdamped) and does not
publish their numbers. Each spec is therefore solved for a damping ratio in the
stated band. `dampingRatio` is exposed so the claim is checkable:

| Spec | k | ζ | undamped period | Character |
|---|---|---|---|---|
| `springSmooth` | 1066 | 0.995 | 0.192 s | critically damped, no overshoot |
| `springSnappy` | 1581 | 0.905 | 0.158 s | small overshoot |
| `springBouncy` | 1206 | 0.705 | 0.181 s | visible overshoot + oscillation |
| `springGesture` | 800 | 0.849 | 0.299 s | carries fling velocity |
| `springStandard` | 131 | 0.830 | **0.549 s** | SwiftUI `.spring()` |
| `springModal` | 180 | 1.006 | 0.468 s | no bounce |
| `springButton` | 1400 | 1.002 | 0.168 s | tap feedback |
| `springDismiss` | 110 | 1.001 | 0.599 s | softer than default |

`springStandard`'s period of 0.549 s is the point: it is the solved stiffness for
the 0.55 s response that **both** sources agree on.

**A disagreement is recorded, not hidden.** Sources differ on SwiftUI's default
damping fraction: **0.825** (Medium) vs **0.75** (Create with Swift, Jan 2026).
Apple publishes neither. This project uses 0.825, the better-damped of the two,
so a wrong guess costs less visual noise than an unexpected bounce. Both are in
`SWIFTUI_SPRING_DAMPING` and `..._ALTERNATE_REPORT`.

`springDismiss` was k=200 — **stiffer** than the default, contradicting its own
comment — and is now k=110, genuinely softer.

### 4. Something that actually runs the spring

Constants alone change nothing while every call site does
`ObjectAnimator.ofFloat(...).setDuration(...)`. Added:

- `spring(spec, target, property, startValue)` → a configured `SpringAnimation`
- `springTo(spec, view, property, targetValue, onEnd)` → cancels the outgoing
  spring first, which is what preserves velocity
- `cancelAllSprings()`

The API was read off `androidx.dynamicanimation` 1.0.0 with `javap` rather than
from memory, and three things differ from what one would guess:

- the property type is **`FloatPropertyCompat`** in `…dynamicanimation.animation`;
  there is no `FloatProperty` class in the artifact
- `SpringAnimation` takes the **start value as a constructor parameter**; there
  is no `setInitialValue`
- `FloatPropertyCompat` has `getValue`/`setValue`, and exposes **no public name
  accessor** (`mPropertyName` is package-private), so the in-flight registry is
  keyed by identity hash — correct because these property objects are singletons

`onEnd` is documented as unusable for chaining: a spring has no fixed duration,
so a chain built on completion drifts.

## Honest scope

This replaces the token layer and provides the mechanism. **Call sites still need
converting** from `ObjectAnimator`/`.animate()` to `springTo` — that is the work
that makes it felt, and it is not done. Until then the new curves apply wherever
`easingStandard`/`easingIOSDefault` were already passed, and the new durations
apply to every existing constant reference.

The claim "this is what iOS 27 does" holds for the **curve control points and the
spring-defaults fact**, which are published. It does **not** hold for the spring
numbers, which are derived from Apple's prose descriptions. That distinction is
in the file header so it cannot be quietly upgraded to "transcribed".

## A note on Kotlin comments

Three separate build breaks in this session came from prose inside KDoc:
a `*/` in a path closes the comment early, and a `/*` in a glob **opens a nested
comment** because Kotlin block comments nest (unlike Java's) — both swallow the
rest of the file and present as `unresolved reference MotionTokens` in unrelated
components, which sends you hunting in entirely the wrong file. The warning is
now at the top of `MotionTokens.kt`.
